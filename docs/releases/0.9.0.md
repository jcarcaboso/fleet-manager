# Fleet Manager 0.9.0

This minor release replaces the dashboard with a device-first design, adds the
Operator API and `fleet` commands behind it, and teaches the Agent to report why
something failed, what machine it runs on and how full its disk is. It contains
breaking changes to the `fleet` command line and to some Operator API responses.
Read [Breaking changes](#breaking-changes) and [Upgrade](#upgrade) before
deploying.

The dashboard is part of the Server image and is served at `/dashboard` on the
same origin, so the Server image is the only thing to publish for it.

## Dashboard

Machines are the main view. Each card shows its status, OS and Agent version,
Targets, check-ins, certificate life and disk usage. A machine's page has
Overview, Installed, Problems, Activity, Security and Settings tabs. Other pages
cover Problems, Deployments, Repository, Models, Enrollment and Audit.

- **Detailed errors.** A failed Target shows the error code with an explanation
  and fix steps, the failed step, the file involved, the Agent's message, how
  many attempts failed and since when, the last revision that worked, and a
  **Retry now** button. Problems can be acknowledged or snoozed.
- **What is deployed.** Each revision shows its commit subject and author, which
  Skills were added, changed or removed, and a row per machine with its
  progress. Activity also lists local changes the Agent repaired.
- **Machine information.** OS, hostname, user, architecture, Agent version,
  install method and service manager, with the upgrade command when an Agent is
  outdated.
- **Disk usage.** A meter on each card and a panel with **Refresh** on each
  machine's page. Disks 85% full or more raise a problem.
- **Add machine** is a three-step enrollment wizard that shows when the machine
  first checks in.

The dashboard needs no build step and is plain JavaScript and CSS under the
existing content security policy.

## Operator API and `fleet` CLI

The Operator API now serves the dashboard and the CLI through the same handlers,
under `/operator/v1` (bearer token) and `/dashboard/api` (session). See the
[Operator API](../technical-design/operator-api.md) and
[Operator protocol](../technical-design/operator-protocol.md).

`fleet` is built for AI clients as well as people. Every command prints one JSON
document, and `fleet doctor` lists every open problem with its explanation and
the commands that fix it. New commands include `nodes show|attempts|checkins|
disk|revoke|remove`, `retry`, `explain`, `errors`, `issues`
`list|ack|snooze|reopen`, `scans`, `revisions list|show`, `rollouts show`,
`audit`, `enrollment links` and `models`. The `fleet-operator` Skill in
`examples/skills/` teaches an AI client to use them, and never to revoke, remove
or delete anything without the person's approval.

Operator tokens can now be limited to `read`, `operate` or `admin` with
`Fleet__OperatorScopes__<name>`. A token without a setting keeps full access.
See [operations hardening](../technical-design/operations-hardening.md).

## Agent

- **Failure detail.** After a failed Attempt, the Agent sends a short message,
  the Target-relative path and the step to the Server. Your home directory is
  replaced by `~`, the Agent state directory by `<state-dir>`, and any other
  absolute path by its last component. Parser errors give a line and column and
  never quote file or credential content.
- **Machine information.** Once after the first poll, then when something
  changes: Agent version, OS name and version, kernel, architecture, hostname,
  user, install method, service manager and state directory. The hostname and
  user identify a person and a machine. The Server keeps only the latest report
  and deletes it with the Node.
- **Disk usage.** One `statvfs` or `statfs` call for the home volume, and for
  the state directory's volume if it is a different disk, after the first poll,
  every 4 hours and when an Operator asks for a refresh. It never scans
  directories. The call runs on one background thread with a time limit, so a
  hung network mount cannot stall polling.
- **Drift.** When the Agent repairs files that changed outside Fleet, it reports
  up to 20 file paths per Target. Nothing is sent about AI-client settings.
- **Read-only commands.** `fleet-agent status`, `targets`, `check` and `disk`
  run while the service holds its lock. They create and change nothing.
  `status` also reports whether the service is running.

All new Agent reports use new routes and are best effort. A failed report never
delays a poll or changes reconciliation, and an Agent talking to an older Server
simply stops reporting. `run.json` is unchanged, so an Agent can be downgraded.

## Breaking changes

- **`fleet` destructive commands need `--yes`.** `nodes revoke`, `nodes remove`,
  `credentials revoke` and `enrollment links revoke` send nothing and exit 2
  without it. `--dry-run` shows the effect.
- **`fleet` output on failure changed.** Errors are one JSON line on stderr:
  `{"error": {"code", "message", "status"}}`. Exit codes are 0 success, 2 usage,
  3 authentication or scope, 4 not found, 5 conflict, 6 other failures and 10
  when `fleet doctor` finds an open error. Scripts that parse the old text or
  rely on the old codes must change. The CLI still never prints Server messages.
- **`GET /dashboard/api/diagnostics` is removed.** Use `GET issues`.
- **Operator API errors and limits.** Every route returns errors as
  `{"code", "message"}`. `limit` must be 1 to 100; larger values, which some
  lists accepted before, return 400 `invalid_request`, as do invalid cursors.
  Operator 401 responses now carry a JSON body. Timestamps end in `Z` instead of
  `+00:00`.
- **The dashboard was rebuilt.** Bookmarks to old sections do not apply, and
  the **Issues to resolve** section is now the **Problems** page.
- **`fleet-agent status` has extra fields** (`service`, `pendingDetail`), and
  the Agent has new commands. Existing fields are unchanged.

## Upgrade

The Server image is `skorcius/fleet-manager:0.9.0`.

1. Take a backup with `scripts/postgres-backup.py`. The Server applies six
   migrations when it starts. They add tables and nullable columns and build
   their indexes without blocking writes. Starting an older image does not
   reverse them; restore the backup to go back.
2. **Upgrade the Server first.** Agents before 0.9.0 keep working. The Server
   gives them exactly the poll and report responses they expect, and they show
   as "not reported" in the dashboard until they are upgraded.
3. Upgrade Agents to 0.9.0 when convenient. Run `fleet-agent service restart`
   after replacing the binary. The dashboard shows each Agent's version, whether
   it is outdated, and the command for how it was installed.
4. Update scripts that call `fleet`, and give automation tokens only the
   scope they need.

For a requested deployment after publication, set
`FLEET_IMAGE=skorcius/fleet-manager:0.9.0` in the installation's `.env`, then
run `docker compose pull` and `docker compose up -d --force-recreate --wait`.
Preserve existing configuration, certificates, credentials, Docker volumes and
Agent state. No re-enrollment is required.

Machine details, disk usage and failure detail appear for a machine only after
its Agent reports them. The macOS code paths for OS version, `uname`, hostname,
user and `statfs` compile in CI but were not run on a Mac before this release.
