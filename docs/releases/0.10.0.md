# Fleet Manager 0.10.0

This minor release moves the Operator dashboard out of the Server into its own
application and container. The dashboard looks and works as in 0.9.0, but it is
now served from its own HTTPS address, by a second image in the same Docker Hub
repository, `skorcius/fleet-manager:dashboard-0.10.0`. This is a breaking change for every
installation: read [Breaking changes](#breaking-changes) and
[Upgrade](#upgrade) before deploying.

The Agent, the `fleet` CLI, the Operator API and the Agent protocol are the same
as in 0.9.0. There is no database migration.

## The separate dashboard

- **Own application.** The dashboard is a Vue 3 and TypeScript application in
  `dashboard/`, with every page and behaviour of 0.9.0. It builds and runs on its
  own, with a mock of the API (`npm run dev:mock`), so it can be developed without
  a Server.
- **Own container.** An unprivileged nginx image serves it over HTTPS, on port
  7444 by default. It runs read-only, as UID 1655, with no capabilities and a
  strict content security policy.
- **Own certificate.** The container has its own certificate and key, issued by
  the installation's CA, and its own volume holding only those and the public CA
  certificate. It cannot read the CA key, the Server key, the database password or
  the Operator token digests.
- **Same sign-in.** Signing in still uses the Operator token and the Server's
  session cookie, and the page never stores the token. The Server accepts
  cross-origin requests from exactly the configured dashboard address
  (`Fleet__DashboardOrigin`) and from nowhere else.
- **Old addresses.** `https://SERVER/dashboard` and anything below it redirect to
  the dashboard address, and old `#/nodes/…` bookmarks open the matching page.
  Enrollment links still point at the Server's `/enroll` page.
- **Tests.** 914 unit and component tests and 149 browser tests run in CI. A
  browser test against a real Server and real Agents runs with
  `scripts/e2e-stack.sh`.

Narrow screens also behave better: every page now fits a 320 px phone without
sideways scrolling.

## Breaking changes

- **The Server no longer serves the dashboard.** It needs the new `dashboard`
  service, published on its own port (7444 by default). Without it, `/dashboard`
  redirects to an address where nothing answers.
- **New setting `Fleet__DashboardOrigin`.** Compose sets it from
  `FLEET_DASHBOARD_URL`. Without it the dashboard API is not served and
  `/dashboard` returns `404 dashboard_not_configured`.
- **Existing installations need `setup.py --add-dashboard`** before
  `docker compose up`. The `configure` step stops with a message when the
  dashboard certificate is missing, and `docker compose up --wait` only reports
  that `configure` failed; `docker compose logs configure` shows why.
- **Same site.** The dashboard and the Server must be on the same site: both
  HTTPS, on the same host or registrable domain. Different ports and subdomains
  are fine. A dashboard on another site cannot sign in and says so.
- **No IPv6-literal addresses for the dashboard.** The content security policy
  cannot express them. Use a DNS name. `setup.py` refuses an IPv6 `--host`.
- **Asset paths.** The Server no longer serves `/dashboard/<file>`. The
  enrollment page's script and stylesheet moved to `/enroll/enroll.js` and
  `/enroll/enroll.css`.

## Upgrade

Upgrade the Server and the dashboard together. Agents do not need an upgrade.

1. Back up PostgreSQL and the private configuration as described in the
   [backup guide](../technical-design/backup-restore.md). This release has no
   migration, so the backup is a precaution.
2. Replace `compose.yaml` with this release's copy. Keep `.env`, `secrets/`,
   `operator.env`, `ssh/` and the Docker volumes.
3. From the deployment directory, run `python3 setup.py --add-dashboard`.
   - It issues the dashboard certificate from the existing CA, and adds
     `FLEET_DASHBOARD_IMAGE`, `FLEET_DASHBOARD_PORT`, `FLEET_DASHBOARD_URL` and
     `DashboardOrigin`, each only if missing.
   - It leaves the CA, the Server certificate, the database password and the
     Operator token unchanged.
   - Add `--dashboard-port` if 7444 is taken.
4. Set `FLEET_IMAGE=skorcius/fleet-manager:0.10.0` in `.env`. The dashboard image
   defaults to `skorcius/fleet-manager:dashboard-0.10.0`.
5. Open the dashboard port on the same interface and firewall as the Server
   port.
6. Run `docker compose pull` and `docker compose up -d --force-recreate --wait`.
7. Open `https://FLEET_HOSTNAME:7444` and sign in.

[Upgrading to the separate dashboard](../../deploy/homelab/README.md) in the
deploy guide has the details.

## Security notes

- Cookies are scoped to a host, not a port. When the dashboard and the Server
  share a host name (the default), the browser also sends the session cookie to
  the dashboard container. A separate host name for the dashboard under the same
  domain avoids that.
- Whoever controls the dashboard container can serve modified code to Operators.
  Pin the dashboard image like the Server image and update both together. See
  [operations hardening](../technical-design/operations-hardening.md).
- Signing out clears the browser's session cookie but does not revoke a copied
  one, as in 0.9.0.

## Verification

- **CI:** the Server, Rust and dashboard unit tests, the dashboard browser tests
  and an image smoke test pass in CI.
- **Real stack:** before release, both images from the release commit run
  together on a disposable stack, checked with:
  - `smoke-https.py`, `smoke-dashboard.py` and the browser journeys against real
    Agents;
  - an upgrade of a 0.9.0 installation with `--add-dashboard`;
  - a check that the dashboard container cannot read the Server's secrets.
- **Not verified:**
  - Real CA trust in a desktop browser. Tests pin the leaf certificates.
  - Revision and rollout pages against a Server with a Git source.
  - The macOS Agent on a real Mac. It is unchanged since 0.9.0.
