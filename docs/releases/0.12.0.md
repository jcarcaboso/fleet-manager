# Fleet Manager 0.12.0

Images: `skorcius/fleet-manager:0.12.0` (Server) and
`skorcius/fleet-manager:dashboard-0.12.0` (dashboard), Linux amd64.

This minor release lets Operators **update the Agent from the dashboard or the
`fleet` CLI** without logging in to the machines, and gives every Agent **one
service command** that runs it from a Fleet-owned copy in its state directory.
Releases are **signed**: the Agent runs only binaries listed in a release
manifest signed with the project's release key.

Agents up to 0.11 cannot update themselves. Upgrade each Node once by hand to
0.12.0 and run `fleet-agent service install`; later releases can then be rolled
out from the dashboard. Read [Upgrade](#upgrade) first. The release has one
database migration.

## Agent updates from the Server

- **Update Agent.** The Machine panel on a machine's page updates one Node;
  **Update outdated Agents** on the machines list updates all or a selection of
  them and shows a result per machine. Failed updates and outdated Agents on
  the Problems pages offer the same action. The machines list and the machine
  page show updates in progress and failures, with the error explained. `fleet nodes update <node>…`,
  `fleet nodes update --all-outdated` and `fleet nodes update --cancel <node>`
  do the same from the CLI. They need the `admin` scope. The target is always
  the Server's own version.
- **Signed and verified twice.** The Server mirrors the signed release of its
  version from GitHub, checks the manifest signature with the release keys
  embedded in it before downloading any archive, and checks every binary
  against the signed digest and size. Each Agent checks the signature again
  with the keys compiled into it, refuses older versions, streams its binary
  with a 64 MiB limit, checks the digest and runs `--version` before it
  switches. Neither the Server nor GitHub alone can make an Agent run a binary.
- **Trial and rollback.** The Agent switches `current`, exits with code 75 and
  the service manager starts the new version. The new version reports success
  after its first successful poll and keeps the previous version. After more
  than three starts, or ten minutes without a successful poll, it switches back
  by itself and the previous version reports the failure.
- **State and problems.** `fleet nodes show` and the dashboard show
  `agentUpdate` (`requested`, `downloading`, `restarting`, `succeeded`, `failed`
  with an error code, or `cancelled`) and whether the Agent can update itself
  (`agent.selfUpdate`). A failed update raises `agent_update_failed` instead of
  `agent_outdated`; `fleet explain <code>` describes each failure.
  `fleet-agent update status` on the Node shows the last update.
- **Offline Servers.** Place the release files in the Server's release cache
  (`Fleet:AgentReleases:CacheDirectory`) instead; the Server verifies them the
  same way. See the [client update guide](../technical-design/client-updates.md#agent-self-update).

## One service command

- **Fleet-owned copy.** `fleet-agent service install` copies the Agent to
  `<state-dir>/versions/<version>/`, points `current` at it, writes a
  `systemd --user` unit or launchd agent that runs `<state-dir>/current/fleet-agent`,
  and starts it. Homebrew, Cargo and archives only supply the first binary.
- **Homebrew services are moved over.** An Agent run by `brew services` is
  stopped and replaced. The Homebrew formula no longer has a service block.
- **New commands.** `service logs [--follow]`, `service uninstall
  --purge-binaries`, `update status` and `update rollback`.
- **Restart=always.** The systemd unit restarts the Agent after any exit, which
  self-update relies on. Run `service install` again to apply it.
- **Install method `managed`.** Telemetry reports it for an Agent run from the
  copy.

## Release signing

Tagged releases publish `fleet-agent-release.json`, with the version, source
commit and the digest and size of each `fleet-agent`, and its Ed25519 signature
`fleet-agent-release.json.sig`, made in the `release-signing` environment. The
[release key guide](../../clients/bins/fleet-agent/release-keys/README.md)
explains how the key is created and rotated.

## Breaking changes

- **Poll responses** may contain `agentUpdate`, but only for Agents that send
  the `agent-update` capability.
- **Node list and detail** gain `agentUpdate`, and `agent` gains `selfUpdate`.
  Clients that reject unknown members must accept them.
- **New Operator routes** `POST nodes/{node}/agent-update`,
  `POST nodes/{node}/agent-update/cancel` and `POST agent-updates` (scope
  `admin`), and Agent routes under `/agent/v1/agent-releases/` and
  `POST /agent/v1/agent-update/report`. The
  [Operator API](../technical-design/operator-api.md#agent-self-update)
  documents them.
- **The Server reaches GitHub** (`Fleet:AgentReleases:BaseUrl`) on the first
  update request of its version.

## Upgrade

Upgrade the Server and the dashboard first, then the Agents.

1. Back up PostgreSQL and the private configuration as described in the
   [backup guide](../technical-design/backup-restore.md).
2. Set both images in `.env`:
   `FLEET_IMAGE=skorcius/fleet-manager:0.12.0` and
   `FLEET_DASHBOARD_IMAGE=skorcius/fleet-manager:dashboard-0.12.0`. The
   Server keeps mirrored releases in `Fleet:AgentReleases:CacheDirectory`
   (default `/var/lib/fleet/agent-releases`), which must be writable by its
   user. The homelab `compose.yaml` already mounts a tmpfs at `/var/lib/fleet`;
   a Compose file of your own needs the same. Run `docker compose pull` and
   `docker compose up -d --force-recreate --wait`. The migration
   `AddAgentUpdates` adds the `agent_updates` table and a `boolean` column with
   a default to `nodes`; it does not rewrite rows.
3. On each Node, install the 0.12.0 Agent the way it was installed first (for
   example `brew upgrade fleet-agent`) and run `fleet-agent service install`.
   `fleet nodes show` then reports `agent.selfUpdate: true`, and from the next
   release the dashboard offers **Update Agent** for it.

An older Agent keeps working with a 0.12.0 Server and never receives the new
poll field. A 0.12.0 Agent against an older Server never receives an update
request, and an older Server refuses its telemetry install method `managed`
until it is upgraded.

## Security notes

- The release key's private half exists only as a GitHub environment secret.
  Agents and Servers trust the public keys committed when they were built;
  rotating the key takes one release that trusts both keys.
- A new version that crashes before it records its start keeps restarting under
  the service manager without rolling back. `fleet-agent update rollback` on the
  Node recovers it, and the dashboard shows the Node as stale and the update as
  `restarting`.

## Verification

- **CI:** the Server, Rust and dashboard unit tests and the dashboard browser
  tests pass.
- **End to end:** `scripts/smoke-agent-update.sh` updates a real Agent through a
  real Server under `systemd --user`, with a release signed by
  `scripts/sign-agent-release.py` and a throwaway key, and checks a crash-loop
  rollback and a successful update.
- **Not verified:**
  - An update with the real release key and a published GitHub release; the
    first release that commits the public key is the first that can be
    checked this way.
  - Updates of a launchd Agent on a real Mac.
