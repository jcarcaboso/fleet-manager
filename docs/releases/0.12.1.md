# Fleet Manager 0.12.1

Images: `skorcius/fleet-manager:0.12.1` (Server) and
`skorcius/fleet-manager:dashboard-0.12.1` (dashboard), Linux amd64.

This patch release publishes the Agent self-update release of
[0.12.0](0.12.0.md). Its only change is to the packaging: the Linux Agent
archive is now built with the Agent's build script and the release public keys,
so `fleet-agent-linux-amd64.tar.gz` embeds the release keys and accepts signed
updates. Everything else is as described in the [0.12.0 notes](0.12.0.md).

## Linux Agent archive

The tag workflow builds the Linux clients with `scripts/build-cli.sh` from a
partial copy of the source. In 0.12.0 that copy left out
`clients/bins/fleet-agent/build.rs` and `release-keys/*.pem`, which compile the
release keys into the Agent, so the Linux build failed. The `v0.12.0` workflow
stopped before signing anything: 0.12.0 has images but no GitHub release, no
client archives, no signed `fleet-agent-release.json` and no Homebrew formulas.

The script now copies both, and stops a tagged build that has no key, because
such an Agent would refuse every update (`agent_update_untrusted`). CI builds
the Linux archives on every change and checks that the packaged Agent embeds
every committed key.

A 0.12.0 Server mirrors the release of its own version, which does not exist,
so it answers every update request with `agent_release_unavailable`. Use 0.12.1
for both the Server and the Agents.

## Upgrade

Upgrade the Server and the dashboard first, then the Agents.

1. Back up PostgreSQL and the private configuration as described in the
   [backup guide](../technical-design/backup-restore.md).
2. Set both images in `.env`:
   `FLEET_IMAGE=skorcius/fleet-manager:0.12.1` and
   `FLEET_DASHBOARD_IMAGE=skorcius/fleet-manager:dashboard-0.12.1`. The
   Server keeps mirrored releases in `Fleet:AgentReleases:CacheDirectory`
   (default `/var/lib/fleet/agent-releases`), which must be writable by its
   user. The homelab `compose.yaml` already mounts a tmpfs at `/var/lib/fleet`;
   a Compose file of your own needs the same. Run `docker compose pull` and
   `docker compose up -d --force-recreate --wait`.
   - **From 0.11:** the migration `AddAgentUpdates` adds the `agent_updates`
     table and a `boolean` column with a default to `nodes`; it does not
     rewrite rows.
   - **From 0.12.0:** there is no migration. Set the two images and pull
     0.12.1.
3. On each Node, install the 0.12.1 Agent the way it was installed first (for
   example `brew upgrade fleet-agent`) and run `fleet-agent service install`.
   This is the one manual Agent upgrade: Agents up to 0.11 cannot update
   themselves, and 0.12.0 published no Agent. `fleet nodes show` then reports
   `agent.selfUpdate: true`, and from the next release the dashboard offers
   **Update Agent** for it.

An older Agent keeps working with a 0.12.1 Server and never receives the new
poll field. A 0.12.1 Agent against an older Server never receives an update
request, and a Server older than 0.12.0 refuses its telemetry install method
`managed` until it is upgraded.

## Verification

- **CI:** the Server, Rust and dashboard tests and the dashboard browser tests
  pass, and the "Linux client archives" job checks that the packaged Agent
  embeds `release-keys/release-2026.pem`.
- **Not verified:**
  - An update with the real release key between two published releases; 0.12.1
    is the first published release that can update itself, so the next release
    is the first that can be checked this way.
  - Updates of a launchd Agent on a real Mac.
