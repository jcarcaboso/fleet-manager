# Fleet Manager 0.12.2

Images: `skorcius/fleet-manager:0.12.2` (Server) and
`skorcius/fleet-manager:dashboard-0.12.2` (dashboard), Linux amd64.

This release makes the Server and dashboard TLS certificates renew themselves,
so an expiring certificate no longer depends on a manual step. It also delivers
Skills to Claude Code's own directory. There is no database migration.

## Claude Code skills

Nodes selecting Claude Code through Agent sources or an AI client connection now
receive the same resolved Skills at `~/.claude/skills`, through a separate
`skills/claude` Target. The configured shared Skills destination remains unchanged
for Codex, OpenCode, and other clients. If it already points at `.claude/skills`,
Fleet does not create a duplicate Target. The dashboard shows both destinations
with their own status.

The Agent announces `claude-skills` in its poll capability header. The Server
withholds the new Target from older Agents, so they keep working after the Server
upgrade. Claude delivery remains pending until the Node runs the updated Agent.
Existing unowned Skills are never overwritten.

Accepted Desired revisions are immutable. For a Claude Node configured before
this upgrade, commit and push a new source revision, then run
`fleet source rescan` to publish its Claude Skills Target. Rescanning the same
already accepted commit does not rebuild its Assignments.

## Automatic renewal

The Server replaces its own certificate, with less than 30 of its 90 days left,
from the CA key it already holds. The new certificate and key exist only in
memory, so this needs no restart and no writable volume, and new connections get
it at once. The configured files only seed it. They may go stale or expire, and a
deployment that copies them back undoes nothing.

The dashboard has no CA key, so the Server replaces its certificate in the
`dashboard-tls` volume and the dashboard reloads nginx. Certificates another CA
signed are left alone. `GET /operator/v1/metrics` reports the expiry of each
certificate and the renewal outcomes. See
[TLS certificates](../technical-design/tls-certificates.md).

## The CA

The CA certificate does not renew itself. An installation created before this
release has a CA that lasts 365 days. From 7 days before it expires, the Server
refuses to start and Node renewals fail. Extend it with `python3 setup.py
--renew-ca`, which keeps the key and subject: every issued certificate stays
valid, and Agents need no change, even after the CA certificate they hold has
expired. New installations get a CA that lasts 10 years.

`setup.py --renew` replaces the Server and dashboard certificates by hand, for a
release that cannot renew them itself.

## Upgrade

Upgrade the Server and the dashboard first, then the Agents.

1. Back up PostgreSQL and the private configuration as described in the
   [backup guide](../technical-design/backup-restore.md).
2. Replace `compose.yaml` and `setup.py` with this release's copies, set
   `FLEET_IMAGE=skorcius/fleet-manager:0.12.2` and
   `FLEET_DASHBOARD_IMAGE=skorcius/fleet-manager:dashboard-0.12.2` in `.env`, then
   run `docker compose pull` and `docker compose up -d --force-recreate --wait`.
   The `configure` service moves `dashboard-tls` to its new ownership.
3. If the installation is older than this release, run `python3 setup.py
   --renew-ca` and repeat `docker compose up -d --force-recreate --wait`.
4. Update Agents from the dashboard or with `fleet nodes update`. Agents do not
   need this for certificate renewal: a 0.12.1 Agent keeps working with a 0.12.2
   Server. Update Agents on Claude Nodes to enable the new Skills destination.
5. Publish a new source revision for existing Claude selections, as described
   above, so their Claude Skills Targets are created.

With a Compose file of your own, the new images work without changes, and the
Server renews its certificate. For the dashboard's, make these changes together:

- Set `Fleet__DashboardCertificateDirectory` on the Server to a path where it
  mounts `dashboard-tls`, read-write.
- Run the dashboard as `user: "1655:1654"`, so it reads that volume through the
  Server's group.
- Give `configure` the block from this release's `compose.yaml`, which keeps a
  renewed certificate, and owns the volume as `1654:1654` with mode `0750`, and
  its files with mode `0640`.

Replacing certificates by hand still needs `--force-recreate`, or any other change
to the service. `docker compose up -d` alone runs `configure` again, but leaves the
running Server on its old certificate, because Compose cannot see inside mounted
secrets.

## Verification

- **Claude Skills:** tests cover client selection, publication, capability-gated
  polling, independent reconciliation, drift repair, removal, and unowned content.
  Dashboard tests cover both Skills destinations and their status.
- **CI:** required checks cover the Server, Rust and dashboard on Linux, and
  Rust on macOS. They must pass for the release commit before tagging.
- **Agent update:** `scripts/smoke-agent-update.sh` passed a successful update
  and a crash-loop rollback under `systemd --user`, with a throwaway release key.
- **Dependency audit:** Cargo audit succeeds with the existing Tokio 1.53.1
  warning `RUSTSEC-2026-0386`, concerning I/O safety in `AsyncFd` constructors.
  The Claude Skills fix does not change the locked Rust dependencies.
- **Stack:** `scripts/smoke-tls-renewal.sh` runs the images with a real Agent through
  expiring certificates, Server certificate changes, Compose reruns and restarts.
- **Upgrade:** a 0.12.1 stack with an enrolled Agent was upgraded in place, keeping
  its volumes, through the image bump, the Compose change and `--renew-ca`. The
  Agent stayed connected with the CA it enrolled with.
- **Not verified before tagging:**
  - An update with the real release key from 0.12.1. It needs this release to be
    published.
  - Updates of a launchd Agent on a real Mac.
